## 3. Повний перелік пунктів класу C (поза периметром) і D (сумнівно)

### 3.1. Клас C — виходить за периметр

**C-1. [web] рівень 3 — «власні фільтри каталогу (Studio)»**  
Джерело: документація 19.0 (пошук).  
Чому: Фільтри магазину штатно — за атрибутами (eCommerce Filter: Visible), тегами товарів і ціною. Поле Studio фільтром на сайті стати не може без коду шаблонів (XML/JS)  
Що робити: «фільтри каталогу за атрибутами, тегами і ціною (штатно)» — прибрати «(Studio)»

**C-2. [pos] рівень 2 — «власні поля в чеку (Studio)»**  
Джерело: документація 19.0 (пошук).  
Чому: Чек POS рендериться у фронтенді POS (OWL/QWeb-JS), не як серверний звіт. Відповідь на odoo.com: «you cannot customize the receipt using the Studio application». Штатно доступний лише власний текст шапки й підвалу (Bills & Receipts → Custom header & footer). Поля на pos.order через Studio додати можна, але на чек вони не потраплять  
Що робити: «власний текст шапки й підвалу чека (штатно); власні поля замовлення POS для бекофісу (Studio)»

**C-3. [rnt] рівень 3 — «технологічна пауза між орендами; облік ТО по екземпляру — доопрацювання»**  
Джерело: документація 19.0 (пошук) + стенд (аудит).  
Чому: Пауза (Padding/Security Time) — штатно. «Облік ТО по екземпляру — доопрацювання» прямо називає кастомізацію, якої департамент не робить, і ставить її в оплачений рівень. Клієнт прочитає як обіцянку  
Що робити: «технологічна пауза між орендами (штатно); ТО об'єктів — заявками в застосунку Обслуговування, без автоматичного зв'язку з орендою»; «доопрацювання» — у стоп-лист

**C-4. [rnt] рівень 3 — «комплектація позиціями з серійниками; шаблон комплекту — доопрацювання»**  
Джерело: стенд (аудит) + моє знання Odoo — гіпотеза.  
Чому: Позиції з серійниками — штатно. Шаблон комплекту як «доопрацювання» — поза периметром. Штатна заміна: шаблони пропозицій (quotation templates) з набором рядків (гіпотеза — перевірити з орендними датами на стенді)  
Що робити: «комплектація позиціями з серійниками; типові комплекти — шаблонами пропозицій»

**C-5. [dsh] рівень 3 — «обчислювані поля на моделі — окрема оцінювана доробка»**  
Джерело: стенд (аудит).  
Чому: Пункт сам каже, що це «доробка» — тобто код, якого департамент не робить, — і стоїть у складі робіт оплаченого рівня 3 (€1700). Клієнт прочитає як «входить, лише оцінять окремо». Це пряме порушення межі з CLAUDE.md  
Що робити: прибрати з рівня; у стоп-лист: «обчислювані поля на моделі — не робимо; показники рахуються формулами Spreadsheet або звітами». Замінити пунктом «зведений дашборд власника з кількох застосунків»

**C-6. [prt] рівень 3 — «поля бланка через Studio; умови всередині бланка — лише в XML»**  
Джерело: документація 19.0 (пошук) + стенд (аудит).  
Чому: Документація 19.0: умови в звіті — тільки через Edit sources (XML, t-if). За політикою периметра XML-правки заборонені. Ознака вибору рівня 3 — «кілька бланків зі складною версткою й умовними блоками» — прямо обіцяє те, що пункт забороняє  
Що робити: ознака рівня → «кілька бланків зі складною версткою; варіанти документа — окремими бланками»; пункт → «поля бланка через Studio; замість умовних блоків — окремі бланки під варіанти»

### 3.2. Клас D — сумнівно, залежить від трактування

**D-1. [base] рівень 3 — «матриця прав за підрозділами»**  
Джерело: документація 19.0 (пошук) + моє знання Odoo — гіпотеза.  
Чому: «Матриця» за підрозділами потребує правил записів (record rules) із доменом за полем підрозділу; таке поле є лише в HR-моделях, у продажах/закупівлях його немає — треба поле Studio + правило. Правила записів редагуються в Settings → Technical → Security (режим розробника) — не Studio, не код, але й не «меню налаштувань»; периметр про це мовчить  
Що робити: «права за ролями і командами; видимість за підрозділом — правилом записів там, де в моделі є поле підрозділу (або поле Studio)»; у CLAUDE.md явно дозволити Technical → Security → Record Rules (домен без Python)

**D-2. [base] рівень 3 — «правила видимості записів»**  
Джерело: документація 19.0 (пошук).  
Чому: Механізм штатний і без коду (домен), але живе в технічному меню, а не в Studio. Залежить від трактування «штатної конфігурації»  
Що робити: лишити, але зафіксувати в периметрі: «правила записів — доменом через Technical → Security; без Python»

**D-3. [crm] рівень 3 — «плани й квоти по менеджерах»**  
Джерело: документація 19.0 (пошук) + моє знання Odoo — гіпотеза.  
Чому: Персональних квот у CRM немає (документація 19.0 описує лише Invoicing Target команди). Target-based плани є в застосунку Commissions — окрема конфігурація, якої позиція не називає  
Що робити: «ціль команди на місяць (штатно); особисті плани — у дашборді Spreadsheet; плани з комісіями — застосунок Комісії, окремо»
Прихована залежність: Commissions (застосунок «Комісії», у прайсі позиції немає); у прайсі — ні; наслідок: налаштування планів комісій — непозначена робота; або квоти лишаються в Spreadsheet

**D-4. [sal] рівень 1 — «рахунок і акт»**  
Джерело: моє знання Odoo — гіпотеза.  
Чому: «Рахунок» — штатний. «Акт» — окремий друкований бланк у Studio (дубль звіту рахунка/замовлення з іншим заголовком і полями); на рівні 1, де Studio за визначенням немає, його не буде. Крім того, акт як первинний документ — це БAS, в Odoo він операційний  
Що робити: «рахунок; акт виконаних робіт — власним бланком у позиції Друковані форми (рівень 2)»
Прихована залежність: prt L2 «два-три власні бланки» (€800); у прайсі — так; наслідок: акт на рівні 1 суперечить визначенню рівня 1 («нічого не змінюємо»): без позиції prt L2 акта не буде

**D-5. [sal] рівень 3 — «комплекти й опції в пропозиції»**  
Джерело: документація 19.0 (пошук) + стенд (аудит).  
Чому: Опційні товари — штатно. «Комплект» у Odoo — це або набір (BoM типу Kit → потребує застосунку Виробництво, підтверджено на стенді), або тип товару Combo (19: доступний у Продажах, фіксована ціна, вибір клієнта — інша семантика, складська поведінка не перевірена)  
Що робити: «опційні позиції в пропозиції (штатно); комбо-товари з фіксованою ціною; набори зі складським розбиранням — потребують застосунку Виробництво»
Прихована залежність: mrp (Виробництво, від L1 €1000); у прайсі — так; наслідок: та сама схована залежність, що вже виправлена у stk L2, але тут не позначена

**D-6. [web] рівень 3 — «власні блоки під бренд»**

Що робити: «брендування штатних блоків: кольори, шрифти, зображення, варіанти теми; нові (кодовані) блоки — поза периметром»

**D-7. [shop] рівень 1 — «один спосіб оплати»**

Що робити: «оплата переказом на рахунок або при отриманні; онлайн-еквайринг — тільки провайдером зі стандартного переліку Odoo, що обслуговує юрособи України (перевіряється до продажу); LiqPay/Monobank/WayForPay/Fondy — немає»

**D-8. [shop] рівень 2 — «кілька способів оплати»**

**D-9. [pos] рівень 1 — «чек і повернення»**

Чому: Odoo POS сертифікований для Бельгії, Франції, Німеччини (документація 19.0); для України фіскалізації (РРО/ПРРО, Checkbox, Вчасно.Каса) у стандарті немає, сторонні модулі на SaaS не ставляться. **D-10. [mrp] рівень 3 — «подання цеху й кнопки етапів (Studio)»**

Що робити: «подання нарядів і замовлень у бекофісі (Studio); цеховий інтерфейс Shop Floor — штатний, не змінюється»

**D-11. [pln] рівень 3 — «навички виконавців і підбір»**

**D-16. [fsm] рівень 3 — «підрядники й субвиконавці»**

Чому: Призначити задачу можна тільки внутрішньому користувачу (кожен — платна ліцензія клієнта). Що робити: «підрядники — як користувачі з ліцензією Odoo (оплачує клієнт); або доступ до задач через Project Sharing без призначення виконавцем»

**D-17. [mnt] рівень 2 — «облік простоїв»**

Чому: «Простій» як окремий об'єкт (початок/кінець, причина) у Maintenance відсутній. Наближення — Duration заявки і MTTR. Повний журнал = поле/модель Studio з ручним внесенням

Що робити: «MTBF, MTTR і прогноз наступної відмови (штатно); лічильник наробки — поле Studio, вручну; залишковий ресурс не обчислюється»

Прихована залежність: stk (Склад); у прайсі — так; наслідок: списання запчастин можливе лише складським переміщенням/списанням поза заявкою

**D-20. [exp] рівень 2 — «ліміти за категоріями»**

**D-21. [exp] рівень 3 — «аванси й підзвітні суми»**

Чому: Українські кадрові документи (накази П-1…П-5, табель, штатний розпис, особові картки) є лише у сторонньому l10n_ua_hr (Apps Store) — на SaaS не ставиться. Клієнт під «кадровими документами» розуміє саме їх

Прихована залежність: doc (Документи й підписи, від L1 €400); у прайсі — так; наслідок: файли співробітників зберігає застосунок Документи

**D-24. [doc] рівень 2 — «маршрути узгодження»**

Чому: Documents 19.0: «Actions on Select» — серверні дії над файлом (перемістити, тегувати, створити запис, запит підпису). Погодження документа = запит у застосунку Погодження з вкладенням, або кроки погодження Studio на кнопці. «Маршрут» як BPM-процес — відсутній

Прихована залежність: Approvals (застосунок «Погодження», позиції немає); у прайсі — ні; наслідок: налаштування типів запитів і погоджувачів не оцінене

**D-25. [doc] рівень 3 — «складні маршрути з умовами»**  
Джерело: документація 19.0 (пошук) + моє знання Odoo — гіпотеза.  
Чому: Studio approvals дозволяють кроки з умовою (фільтр біля Approvers), порядок кроків і ексклюзивність — на кнопці моделі. У Approvals категорія має фіксований список погоджувачів. «Складний маршрут з умовами» в розумінні клієнта (розгалуження, ескалації, паралельні гілки) — не робиться  
Що робити: «кроки погодження з умовами й порядком на кнопці запиту (Studio approvals); маршрути з розгалуженнями й ескалаціями — немає»
Прихована залежність: Approvals; у прайсі — ні; наслідок: див. L2

**D-26. [doc] рівень 3 — «шаблони документів»**  
Джерело: моє знання Odoo — гіпотеза.  
Чому: Клієнт під «шаблонами документів» часто розуміє генерацію договорів із підстановкою реквізитів. В Odoo це — або шаблон Sign із полями для заповнення, або друкований бланк Studio з запису (позиція prt). Генератора .docx немає  
Що робити: «шаблони для підпису (Sign) і шаблони таблиць; документ із реквізитами запису — друкованим бланком (Друковані форми)»

## 5. Критичність знахідок

**Критично — клієнт заплатить за те, чого не буде**

1. **[pos] уся позиція** — чек Odoo нефіскальний, фіскалізації для України на SaaS немає. Роздріб B2C без ПРРО працювати не може; це не пункт, а умова продажу позиції.
2. **[pos] р.2 «власні поля в чеку (Studio)»** — Studio чек не редагує (C).
3. **[shop] р.1 «один спосіб оплати», р.2 «кілька способів оплати»** — у стандарті немає жодного українського еквайрингу; для UA гарантовано лише переказ і оплата при отриманні.
4. **[dsh] р.3 «обчислювані поля на моделі — окрема оцінювана доробка»** — код усередині оплаченого рівня (C); прямо суперечить CLAUDE.md.
5. **[prt] р.3 «умови всередині бланка — лише в XML» + ознака рівня «з умовними блоками»** — рівень продає те, що пункт забороняє (C).
6. **[rnt] р.3 два пункти з «доопрацювання»** — розробка всередині фіксу (C).
7. **[sal] р.1 «рахунок і акт»** — акта на рівні 1 не буде без Studio-бланка (позиція prt р.2).
8. **[sal] р.3 «комплекти й опції»** — та сама залежність від Виробництва, що вже виправлена у Складі, тут не позначена.
9. **[exp] р.3 «аванси й підзвітні суми»** — об'єкта немає; клієнт з UA очікує саме підзвіт.
10. **[fsm] р.3 «підрядники й субвиконавці»** — кожен підрядник = ліцензія клієнта, інакше урізаний портальний доступ.
11. **[doc] р.2 «маршрути узгодження», р.3 «складні маршрути з умовами»** — рушія маршрутів немає; потрібен застосунок Погодження, якого в прайсі немає.
12. **[stk] р.3 «кілька складів; розмежування доступу — через окремі юрособи»** — «окремі юрособи» = позиція mco (від €500), яку клієнт міг не купити.

**Важливо — обіцянка ширша за механіку, треба звузити формулювання**

- [web] р.3 «власні блоки під бренд» (нові блоки = код) і «власні фільтри каталогу (Studio)» (фільтри лише за атрибутами/тегами/ціною).
- [shop] р.2 «кілька способів доставки й тарифи» — автотарифи й ТТН Нової Пошти/Укрпошти відсутні; р.3 «наявність зі складів», «самовивіз» — тягнуть stk р.3.
- [pln] р.3 усі три змістові пункти (навички/підбір, вирівнювання, прогноз) — Auto Plan працює за ролями і доступністю, більше нічого.
- [mnt] р.2 «облік простоїв», р.3 «метрики наробки й ресурсу», «облік запчастин» — лічильників, ресурсу і запчастин у Maintenance немає.
- [fsm] р.2 «маршрути на день», р.3 «планування за геолокацією» — карта і сортування за часом; маршрут лише з токеном MapBox клієнта; оптимізації немає.
- [crm] р.3 «плани й квоти по менеджерах» — квоти на менеджера лише через застосунок Комісії або таблицю.
- [hr] р.3 «кадрові документи» — українські накази/табель/штатний розпис — поза периметром.
- [mrp] р.3 «подання цеху (Studio)» — Shop Floor Studio не редагує.
- [exp] р.2 «ліміти за категоріями» — лише як умовний крок погодження; блокади немає. р.3 «звірка з картками» — автосинхронізація для банків UA не гарантована.
- [doc] р.2 «електронний підпис» — простий е-підпис, не КЕП; р.3 «шаблони документів» — генератора документів із реквізитами немає.
- [sub] р.1 «регулярний рахунок» — виставляється автоматично, але автосписання оплати для UA недоступне.
- [dsh] р.3 «Digest» — лише штатні KPI.
- [base] р.3 «матриця прав за підрозділами» — лише правилами записів там, де є поле підрозділу.

**Дрібне — уточнення периметра або позначки**

- Пункти без позначки «(Studio)», хоча це Studio: [crm] р.2 «автоматичні активності за стадіями», [sal] р.3 «узгодження знижок за рівнями», [exp] р.3 «кілька рівнів узгодження». На здійсненність не впливає, впливає на визначення рівня («рівень 1 — без Studio»).
- Механізми, що живуть у Settings → Technical (режим розробника), а не в Studio: правила записів ([base] р.3), послідовності ([prt] р.1), шаблони листів ([base] р.2). Без коду, але периметр про це мовчить — треба один рядок у CLAUDE.md.
- Кнопки Studio: дозволити лише «Run a Server Action» з діями без коду; «Call a method» і «Execute Code» — у стоп-лист.
- [shop] р.2 «поля варіантів і атрибутів (Studio)» — атрибути штатні, Studio тут зайвий у формулюванні.
- [acc] р.3 «власні подання звірки (Studio)» — віджет звірки не редагується; лише списки.
- Пункти з залежностями без цінового наслідку (застосунок ставиться автоматично): [pur] р.1 приймання → Склад, [prj] р.2 ставка години → Співробітники.
