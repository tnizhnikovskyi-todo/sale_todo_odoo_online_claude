Дата: 02.09.2026. Предмет: `data/price.json` (26 позицій × 3 рівні), `tools/build_calculator.py`,
`artifacts/calculator.html`. Лінза: що кожна позиція тягне за собою в Odoo 19 Enterprise (Odoo Online,
план Custom), як це ламає тезу «модулі складаються лінійно», і який механізм залежностей додати.

**Як перевірялося — позначки впевненості в тексті і таблицях:**

| **Д** | підтверджено документацією odoo.com/documentation/19.0 (пошук 02.09.2026; сторінки в розділі «Джерела») |

## 0. Головне

1. **Лінійності немає ні технічно, ні економічно.** З 26 позицій 19 тягнуть застосунки, за налаштування яких
   відповідає інша позиція або яких у прайсі немає взагалі. Знайдено **58 залежностей** (з них 16 жорстких —
   без цільової позиції пункт складу робіт технічно неможливий), проти семи, названих в аудиті.
2. **Найбільша дірка — не kits, а Invoicing.** Застосунок «Рахунки» (`account`) встановлюють Продажі, Закупівлі,
   Каса, Інтернет-магазин, Підписки, Оренда, Витрати (Ф) і вимагають «рахунок» у складі робіт, але
   налаштування журналів, ПДВ, умов оплати й банку не належить жодній позиції: «Управлінський облік» — це
   кешфлоу і P&L, а не журнали. Ця робота або робиться в ціні кожної з семи позицій (і тоді рахується
   кілька разів), або не робиться ніким.
3. **Другий за вагою — Співробітники (`hr`).** Таймшити, Витрати, Планування, Виїзні роботи, каса з касирами,
   цех — усі потребують карток співробітників (Ф для `hr_timesheet`, `hr_expense`, `pos_hr`). У Базі карток
   немає, у прайсі вони лише в «Персонал і відпустки» разом із відпустками.
4. **Мультикомпанійність — множник, а не позиція.** Склади, журнали, каси, прайси, послідовності створюються
   на кожну юрособу окремо (Д: склади для другої компанії Odoo не створює автоматично). 10–26 годин mco не
   покривають повторення роботи інших позицій; це найбільше структурне заниження в прайсі.
5. **Калькулятор сьогодні не знає про жодну залежність:** `state.sel[m.id] = !!m.req` — єдина логіка;
   він збирає «Каса без Складу», «Підписки без Продажів», «Виробництво без Складу», «Оренда без Продажів»
   і 20 інших некогерентних наборів без слова попередження (розділ 5).
6. **Закриття залежностей за поточним текстом прайсу дає:** Каса Стандарт €1 600 → €2 600, Підписки Базові
   €1 200 → €1 900, Виробництво Базове €1 600 → €2 600, Магазин Базовий €1 800 → €2 500, Проєкти Стандарт
   €2 000 → €2 700, Оренда Стандарт **€1 600 → €5 700** (каскад: Продажі + Склад рівня 3 + Виробництво через
   набори). Остання цифра показує, що частина залежностей — не факт життя, а наслідок того, куди в прайсі
   покладено пункт (серійники — на рівень 3 Складу, набори — у Склад замість Виробництва).
7. **Пропозиція:** поля `apps`, `home`, `dep` (+ `mult` для mco) у `price.json`; перевірка в
   `build_calculator.py` (готовий `check_deps.py`, 0 помилок на поточному прайсі, 8 змістовних попереджень);
   у калькуляторі — гібрид: жорсткі залежності додаються автоматично з поясненням, логічні — попередження,
   «одна з» — зупинка з підказкою. Плюс нова позиція «Рахунки та податки» замість розширення Бази і чотири
   переносення пунктів між позиціями.
8. **Ліцензії:** план Custom обов'язковий (Studio, кілька компаній, зовнішній API — усі три причини наші), ціна
   лише за внутрішнього користувача, кількість застосунків на ціну не впливає, портальні користувачі
   безкоштовні (Д, odoo.com/pricing, 02.09.2026). Актуальна цифра за користувача пошуком не підтверджена —
   брати з odoo.com/pricing із країною «Україна» перед кожною пропозицією.

### 2.1 Повна таблиця

Разом: **16 жорстких технічних** залежностей між позиціями (у 12 позиціях), **~25 логічних**, **~15 прихованих
застосунків**, **4 дублі**. Аудит назвав сім — вони всі тут (stk→mrp, pur→approvals, mrp→hr, stk→acc та інші),
але це менш як чверть.

### 2.2 Три висновки з таблиці

- **`account` — центр графа.** Його тягнуть sal, pur, pos, shop, sub, rnt, exp, а також prj (2), fsm (3), loyalty.
  Жодна позиція за нього не відповідає. Це головна причина, чому позиції «з рахунками» не складаються лінійно:
  кожна несе свою частку невидимої роботи з обліку.
- **`hr` — другий центр.** prj, exp, pln, fsm, pos (2), mrp (3), mnt. Позиція hr продається як «картки + відпустки»,
  а потрібні лише картки — і майже всім.
- **stk — третій.** pos, mrp, rnt, shop (3), fsm (3), mig (3), pur — і саме тут найдорожчі примусові
  додавання (€1 000–2 400).

## 3. Перевірка тези «модулі складаються лінійно»

Теза з `docs/рішення.md`: «Модулі складаються лінійно, бо спільна частина винесена в Базу і оплачується один раз».
Перевірка: спільна частина, яка реально повторюється між позиціями, — це не те, що лежить у Базі (компанія,
користувачі, контрагенти, пошта), а Invoicing, співробітники, одиниці виміру, календар, склад за
замовчуванням. Їх у Базі немає. Тому лінійність порушується в обидва боки.

### 3.1 Де сума позицій **занижує** обсяг (стик процесів) — гіпотези годин

| Набір | Що з'являється на стику, чого немає в жодній позиції | Оцінка, год |
|---|---|---|
| sal + stk | політика рахунків (за замовленим / за відгруженим), резервування, одно-/двокрокова відгрузка, типи товарів | +3–6 |
| pur + stk | кроки приймання, **правила поповнення (мін/макс)** — не згадані ні в pur, ні в stk | +3–5 |
| sal + pur + stk (торгівля) | маршрути «Купити», MTO, дропшип | +4–8 (частково перекриває два попередні) |
| sal + mrp (+ stk) | маршрут «Виробити на замовлення», набори в КП, специфікації для продажу | +3–5 |
| prj + sal | політика створення проєкту/задачі із замовлення, послуги «за таймшитами», продукт таймшитів, етапи (milestones) | +3–5 (частина вже в prj 2) |
| prj + hlp | таймшити на заявках, заявка → задача | +2–3 |
| pos + stk + acc | облік каси: журнали каси/банку, контроль готівки, ПДВ на чеках, закриття зміни | +3–5 |
| shop + sal + stk | перевізники й тарифи, наявність, політика рахунків, повернення | +3–5 |
| exp + acc + hr | журнал витрат, рахунки категорій, виплата компенсацій, керівники | +2–3 |
| sub + acc | платіжний провайдер, автосписання, нагадування, реєстрація оплат | +2–4 |
| fsm + sal + stk | склади виконавців, продукти-послуги для T&M, політика рахунків з наряду | +3–5 |

| будь-який набір ≥ 6 позицій | права доступу для нових застосунків, наскрізна демонстрація, порядок налаштування (Studio-поля до імпорту) | +5–10 % |

Окреме спостереження: `docs/рішення.md` каже «від шести позицій підсумок дивимо окремо», а калькулятор
попереджає лише `count >= 8` (рядок 1761 `calculator.html`) — і лічить у `count` Базу й Діагностику.
Порогові значення треба узгодити.

застосунках (rnt, sub, pos, mrp, fsm 3, shop), і для мультикомпанійності лінійність не тримається взагалі.

## 4. Що неявно передбачає «База»

Пункти, які інші позиції вважають зробленими, але яких у складі Бази (5 базових + 4 + 5 пунктів) немає:

| Передумова | Хто на неї спирається | Де це в прайсі зараз |
|---|---|---|
| **Рахунки та податки**: журнали продажів/купівель/банку/каси, ставки ПДВ з `l10n_ua` на товарах і контрагентах, умови оплати, банківські реквізити, фіскальні позиції (неплатник, експорт), нумерація й бланк рахунку | sal, pur, pos, shop, sub, rnt, exp; prj (2), fsm (3); acc як надбудова | **ніде**: acc — рух коштів і P&L; sal — «рахунок і акт» одним рядком |
| **Одиниці виміру й категорії товарів** (`uom`, `product.category`) | sal, stk, pur, mrp, pos, shop, rnt, mig (2) | ніде явно; stk має «номенклатура з одиницями виміру» — дубль із Базою («довідник номенклатури») |
| **Модель товару взагалі** (`product`) | «довідник номенклатури» в Базі | Ф: `product` не входить у `base`/`contacts`/`mail` — без товарної позиції Базі нема де завести номенклатуру |

журнали), а винести «Рахунки та податки» в окрему позицію, яку жорстко тягнуть позиції з рахунками; у Базу

## 6. Механізм залежностей

### 6.1 Нові поля в `price.json`

Чотири поля на рівні позиції (усі необов'язкові, щоб не ламати поточний валідатор):

| Поле | Тип | Зміст |
|---|---|---|
| `apps` | `{"1": [...], "2": [...], "3": [...]}` | технічні назви модулів Odoo, які позиція встановлює або вимагає; ключ — рівень, з якого модуль з'являється. Дає (а) чесний список «що встановиться» для тексту пропозиції, (б) чек-лист для `apply-config`, (в) матеріал для механічної перевірки залежностей |
| `home` | `["stock"]` | модулі, за налаштування яких відповідає ця позиція. Правило валідатора: якщо позиція X тягне модуль із `home` позиції Y — у X мусить бути `dep` на Y. Так забуті залежності знаходяться автоматично, а не з голови |
| `dep` | список `{on, type, from_lv, min_lv, why}` | `on` — id або список id («достатньо однієї з»); `type` — `hard` (технічно неможливо без; калькулятор додає сам) або `soft` (неповно/безглуздо без; калькулятор попереджає); `from_lv` — рівень цієї позиції, з якого залежність діє; `min_lv` — мінімальний рівень цільової (типово 1); `why` — одне речення для сейла й тексту пропозиції |
| `mult` | `{"1": 0.25, "2": 0.35, "3": 0.5}` | лише для mco: множник до годин інших вибраних компанієзалежних позицій. Значення — гіпотеза до пілоту |

База — корінь: у `dep` її не пишуть, валідатор забороняє посилання на `req`-позиції.

Готовий фрагмент для всіх 26 позицій — у Додатку A (файл `deps-fragment.json`, 58 записів `dep`). Правила
формулювання, яких я дотримувався: `hard` — тільки те, що підтверджено Ф/Д/С; усе, де рішення за аналітиком
(товарний чи сервісний бізнес, чи потрібен сайт під магазин, чи є співробітники), — `soft`. Кілька записів на
одну пару (наприклад pos → stk soft з рівня 1, hard з рівня 2, hard з `min_lv` 3 з рівня 3) — норма: діє
найсильніший застосовний.

### 6.2 Перевірка в `build_calculator.py`

Готовий скрипт `check_deps.py` (Додаток B) читає той самий `price.json`, приймає поля або вшитими в позиції,
або з окремого фрагмента для проби. Що перевіряє:

- **помилки (збірку скасувати):** `on` посилається на невідомий id, на саму себе або на `req`-позицію; `type`
  не `hard`/`soft`; `from_lv`/`min_lv` поза 1..3; порожнє `why`; `apps` не об'єкт з ключами "1"–"3"; один
  модуль є `home` двох позицій; **позиція тягне модуль із чужого `home` без відповідного `dep` або з `dep`,
  що починається пізніше за рівень, де модуль з'являється**;
- **попередження (ознаки поганого скоупінгу):** примусова позиція дорожча за ту, що її тягне; взаємна жорстка
  залежність (цикл); `hard` «одна з»; База тягне чужий домашній модуль (дубль роботи);
- **демонстрація:** закриття контрольних наборів із ціною «до → після», автододаваннями, підняттями рівня і
  попередженнями — саме те, що має показувати калькулятор.

Вбудовування в `build_calculator.py` — три рядки в `main()` після `check(groups)`:

```python
from check_deps import check_deps            # покласти check_deps.py у tools/
items = {it['id']: it for g in groups for it in g['items']}
dep_errs, dep_warns = check_deps(items)
if dep_errs: errs += dep_errs                # падаємо так само, як на зламаній структурі
for w in dep_warns: print('  ⚠', w)          # попередження — у консоль, збірку не зупиняють
```

Вивід на поточному `price.json` + фрагменті (Додаток C): **0 помилок, 8 попереджень**, і всі вісім — реальні
знахідки, а не шум:

1. `rnt` рівня 2 (€1 000) тягне `stk` рівня 3 (€2 400) — серійники лежать на рівні 3 Складу;
2. `pos` рівня 3 (€1 600) тягне `stk` рівня 3 (€2 400);
3. `sub` рівня 1 (€600) тягне `sal` (€700) — підписки без Продажів не існують, і це дорожче за самі підписки;
4. `mco` рівня 3 (€1 300) тягне `acc` рівня 2 (€1 500);
5–6. взаємна жорстка залежність `stk ↔ mrp` — набори покладено в Склад, а живуть у Виробництві;
7. База тягне `spreadsheet_dashboard` — дубль із Дашбордами;
8. `pln → prj|fsm` — «одна з»: калькулятор не має вибирати за аналітика.

### 6.3 Поведінка калькулятора: автододавання, попередження чи блокування

Три варіанти й що з ними не так для сейла:

| Варіант | За | Проти |
|---|---|---|
| **Блокування** (не дати вибрати Y без X) | ціна завжди коректна | сейл у тупику посеред розмови; клієнт бачить «не можна» замість цифри; для 16 жорстких залежностей це 16 тупиків |
| **Лише попередження** | нічого не нав'язує | сховані залежності — саме те, чого сейл **не знає**; два наявні прапорці (`f-mix`, `f-proj`) уже інформаційні й ні на що не впливають; ціна, названа клієнту, лишається без обов'язкової роботи → збиток на фіксі |
| **Автододавання** | клієнт одразу бачить чесну ціну; сейл не мусить знати граф | виглядає як апсейл, якщо не пояснити; небезпечне для спірних залежностей (товарний чи сервісний бізнес) |

Пропозиція — **гібрид, прив'язаний до `type`:**

- `hard` з одним `on` → **автододавання** цільової позиції на мінімальному достатньому рівні (`min_lv`, а не
  дефолтний індекс 1 «Стандарт», який ставить `blank()`), з тегом у рядку «потрібна для «Точка продажу»» і
  `why` у підказці; чекбокс доданої позиції вимкнений, доки її хтось тягне; якщо цільова вже вибрана, але
  рівень нижчий за `min_lv` — рівень піднімається з повідомленням, а кнопки нижчих рівнів блокуються з
  поясненням. Зняття позиції, що тягла, знімає автододані, якщо їх не вибирали руками (`state.auto`).
- `hard` зі списком `on` («одна з») → **зупинка з підказкою**: прапорець `bad` «оберіть Проєкти або Виїзні
  роботи», підсумок позначається «неповний», у тексті пропозиції — рядок «потребує рішення». Вибір за
  аналітиком, не за скриптом.
- `soft` → **попередження** списком під підсумком і в `summary()` («Точка продажу без Складу: …»); не
  зупиняє. Це матеріал для діагностики: аналітик іде на зустріч із готовим переліком питань.
- `mult` (mco) → окремий прапорець `warn` «Мультикомпанійність множить роботу компанієзалежних позицій;
  орієнтовно +N год» і, після пілоту, — коефіцієнт у ціні.
- `summary()` доповнити двома блоками: «Додано через залежності» (з `why`) і «Встановлені застосунки Odoo»
  (з `apps`) — клієнт бачить, що саме з'явиться в його базі, а Claude отримує чек-лист для `apply-config`.
  І замінити «підписка Odoo (оформлює клієнт)» на «підписка Odoo Online, план Custom (оформлює клієнт)».

Ескіз логіки (замість поточного `render()` перед підрахунком; `state.auto[id]` — хто додав):

```js
function resolve(){
  var notes = [], changed = true;
  Object.keys(state.auto).forEach(function(id){          // спочатку прибрати те, чого вже ніхто не тягне
    if(!state.manual[id]) { state.sel[id] = false; delete state.auto[id]; }
  });
  while(changed){ changed = false;
    MODS.forEach(function(m){
      if(!state.sel[m.id]) return;
      (m.dep || []).forEach(function(d){
        if(d.from_lv - 1 > state.lv[m.id]) return;         // залежність ще не діє на цьому рівні
        var ons = [].concat(d.on), have = ons.filter(function(t){ return state.sel[t]; });
        var need = (d.min_lv || 1) - 1;
        if(d.type === 'hard'){
          if(!have.length){
            if(ons.length === 1){ state.sel[ons[0]] = true; state.lv[ons[0]] = Math.max(state.lv[ons[0]] || 0, need);
                                   state.auto[ons[0]] = m.id; changed = true; }
            else notes.push({kind:'stop', from:m, dep:d});
          } else have.forEach(function(t){
            if(state.lv[t] < need){ state.lv[t] = need; changed = true; notes.push({kind:'raise', from:m, to:t, lv:need}); }
          });
        } else if(!have.length) notes.push({kind:'warn', from:m, dep:d});
      });
    });
  }
  return notes;                                            // render() малює теги, прапорці й блоки summary()
}
```

Референсна реалізація тієї самої логіки на Python — функція `resolve()` у `check_deps.py`; її вивід у Додатку C
— це очікувана поведінка калькулятора на 12 контрольних наборах.

### 6.4 База, «Рахунки та податки» і чотири переносення

**Не розширювати Базу журналами.** База обов'язкова для всіх; клієнт із CRM + Проєктами платив би за ПДВ і
журнали, яких не використовує. Замість цього — **нова позиція `inv` «Рахунки та податки»** в групі «Основа»,
не `req`, але `hard` для всіх, хто виставляє рахунки. Ескіз (години — гіпотеза до заміру у фазі 0):


Після цього `home: ["account"]` змушує валідатор вимагати `dep` на `inv` у кожній позиції, де `account` є в
`apps` — sal, pur, pos, shop, sub, rnt, exp (з рівня 1), prj (з 2), fsm (з 3), acc (з 1; acc — надбудова над
inv, а не дубль). Усі теперішні `soft → acc` з формулюванням «Invoicing» стають `hard → inv`, а `acc`
лишається тим, чим є, — управлінським обліком.

**У Базу додати дешеве й універсальне** (гіпотеза +2–4 год на рівень або переконатися у фазі 0, що це вже
всередині поточних 12/16/24): одиниці виміру й категорії товарів; валюти й курси; робочий календар компанії
зі святами; українська мова інтерфейсу й переклад власних полів. І прибрати з Бази рівня 3 «кілька складів
або офісів у структурі» → «кілька офісів або підрозділів у структурі компанії» (склади — у stk).

**Чотири переносення пунктів, які знімають найдорожчі примусові каскади:**

1. «комплектація наборів» зі stk 2 → у mrp 1 як «набори (kit) без виробничого замовлення»; у stk 2 лишити
   посилання. Знімає взаємну залежність stk ↔ mrp і +€1 000 у кожній торгівлі зі Складом рівня 2.
2. «облік партій або серійних номерів» зі stk 3 → у stk 2 (партії потрібні харчовим, аптечним, сервісним SMB
   без кількох складів). Тоді rnt 2 тягне stk 2 (€1 600), а не stk 3 (€2 400).
3. Картки співробітників: у prj, exp, pln, fsm додати в `inc` «картки співробітників-виконавців (без
   кадрового обліку)» (+1–2 год кожній) і лишити `soft → hr`. Альтернатива — розбити hr на «Співробітники»

4. Поріг «стику»: узгодити `docs/рішення.md` (6) і калькулятор (8) і не рахувати в `count` Базу й Діагностику.

## 7. Ліцензійний наслідок: план Odoo Online Custom

**Підтверджено пошуком по odoo.com (сторінка odoo.com/pricing і її FAQ, зчитано 02.09.2026):**

- Два платні плани — Standard і Custom; «The custom plan is for companies that want to manage multiple companies
  on a single database and that need to customize Odoo through Odoo Studio, custom developments or through the
  API». **Усі три причини — наші:** Studio у кожному рівні «Стандарт»/«Розширений», mco, і Claude працює через
  зовнішній API (FAQ: виклик, ініційований з Odoo назовні, — не «External API»; наш ініціюється ззовні — отже
  «External API»).
- «If you install Studio or add companies to your database, you will automatically switch to the Custom plan» —
  перехід автоматичний, клієнт не може лишитися на Standard «випадково».
- Ціна — **за користувача на місяць**, кількість застосунків на ціну не впливає («whether you install three apps
  or seventy»; «You can install all the Odoo apps you want»). Отже сховані застосунки з розділу 2 — це **наша**
  трудова проблема, а не ліцензійна проблема клієнта; аргумент «додатковий застосунок вам нічого не коштує в
  підписці» правдивий.
- Зовнішні користувачі через портал (клієнти, постачальники) — **не платні**.
- Ціна залежить від країни/регіону та кількості користувачів; згадка в форумі odoo.com про регіональні тарифи
  Standard «7.25 / 13.50 / 19.90» — неофіційна й без дати, не використовувати.

**Не підтверджено:** сама цифра за користувача для Custom у 2026 році пошуком не дісталася (ліміт пошуку
вичерпано, odoo.com для прямого читання заблоковано). З пам'яті за 2024–2025 у євро-зоні це було близько
€19.90 (Standard) / €29.90 (Custom) за користувача на місяць при річній оплаті, місячна — дорожча; **це
неперевірена довідкова цифра**, а не факт. Перед кожною пропозицією брати актуальне значення з odoo.com/pricing
із вибраною країною «Україна» і фіксувати дату. Це саме той пункт, що вже стоїть у концепції (рядок 1179
`concept_text.txt`: «Звірити з чинним прайсом Odoo… скільки він коштує клієнту на рік»).

**Що казати клієнту:**

1. План — Custom, без варіантів; це не наш вибір, а умова Studio й нашого інструменту. Річна вартість
   підписки = внутрішні користувачі × ціна за користувача × 12 — і при 15–20 користувачах вона одного порядку
   з ціною впровадження, тому має звучати на діагностиці, а не після.
2. **Кількість користувачів — головна ліцензійна змінна, і позиції прайсу її змінюють по-різному:**
   - Проєкти й таймшити, Виїзні роботи: кожен, хто списує час, — платний користувач (таймшит створює користувач);
   - Витрати: співробітник може подавати витрати листом на аліас без користувача (А), узгоджувальники — користувачі;
   - Планування: працівники бачать і приймають зміни за посиланням із листа без входу (А), планувальники — користувачі;
   - Каса: касири входять за PIN як співробітники (`pos_hr`, Ф), користувач потрібен на касу, а не на касира;
   - Сервісні заявки, Підписки, Магазин, Продажі (підпис КП): клієнти — портал, безкоштовно;
   - Мультикомпанійність: користувач один на всі компанії, платити двічі не треба.
   Ознаки в Базі («до 5 / до 20 / понад 20 користувачів») — це водночас і ліцензійний коридор клієнта; сейл
   має називати обидві цифри разом.
3. Застосунки не тарифікуються: список «що встановиться» з `apps` можна показувати відкрито — він не лякає
   ціною, а пояснює межі.
4. Odoo Online оновлює версію сам (19.0 → 19.x): інструкції клієнту прив'язувати до версії (уже в аудиті).

## Додаток B. `check_deps.py` — перевірка й референсна логіка закриття

Файл: `docs/аналіз-прайсу/скрипти/check_deps.py`. Запуск: `python3 check_deps.py data/price.json deps-fragment.json`
(другий аргумент зайвий, коли поля вже вшиті в `price.json`).

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""Перевірка залежностей між позиціями прайсу.

Читає data/price.json (як build_calculator.py) і поля apps/home/dep/mult —
або вже вшиті в позиції, або з окремого фрагмента (аргумент 2, для проби).
Друкує помилки (збірку треба скасувати), попередження (ознаки поганого
скоупінгу) і закриття кількох контрольних наборів із цінами.
"""
import io, json, sys

RATE = 50
def price(it, lv_idx):                       # так само, як у калькуляторі
    return round(it['lv'][lv_idx][1] * RATE / 50) * 50

def load(price_path, frag_path=None):
    payload = json.load(io.open(price_path, encoding='utf-8'))
    items = {it['id']: it for g in payload['групи'] for it in g['items']}
    if frag_path:
        frag = json.load(io.open(frag_path, encoding='utf-8'))['позиції']
        for iid, extra in frag.items():
            if iid not in items:
                raise SystemExit('фрагмент посилається на невідому позицію: %s' % iid)
            items[iid].update(extra)
    return items

def as_list(x):
    return x if isinstance(x, list) else [x]

def check_deps(items):
    errs, warns = [], []
    roots = {iid for iid, it in items.items() if it.get('req')}
    home_of = {}
    for iid, it in items.items():
        for m in it.get('home', []):
            if m in home_of:
                errs.append('модуль %s є home одразу у %s і %s' % (m, home_of[m], iid))
            home_of[m] = iid
    for iid, it in items.items():
        apps = it.get('apps', {})
        deps = it.get('dep', [])
        if not isinstance(apps, dict) or set(apps) - {'1', '2', '3'}:
            errs.append('%s: apps мусить бути об’єктом з ключами "1","2","3"' % iid)
            apps = {}
        for d in deps:
            ons = as_list(d.get('on'))
            for o in ons:
                if o not in items: errs.append('%s: dep на невідому позицію %s' % (iid, o))
                if o == iid: errs.append('%s: залежність від самої себе' % iid)
                if o in roots: errs.append('%s: залежність від обов’язкової %s зайва — вона неявна' % (iid, o))
            if d.get('type') not in ('hard', 'soft'):
                errs.append('%s → %s: type мусить бути hard або soft' % (iid, ons))
            if d.get('from_lv') not in (1, 2, 3):
                errs.append('%s → %s: from_lv мусить бути 1..3' % (iid, ons))
            if d.get('min_lv', 1) not in (1, 2, 3):
                errs.append('%s → %s: min_lv мусить бути 1..3' % (iid, ons))
            if not d.get('why'):
                errs.append('%s → %s: порожнє why' % (iid, ons))
            if len(ons) > 1 and d.get('type') == 'hard':
                warns.append('%s → %s: hard-залежність «одна з» — калькулятор не додасть сам, лише зупинить із підказкою' % (iid, ons))
            # сигнал завищення: примусова позиція дорожча за ту, що її тягне
            if d.get('type') == 'hard' and len(ons) == 1 and ons[0] in items:
                tgt = items[ons[0]]
                if price(tgt, d.get('min_lv', 1) - 1) > price(it, d['from_lv'] - 1):
                    warns.append('%s (рівень %d, €%d) тягне %s рівня %d за €%d — примусова позиція дорожча за саму позицію'
                                 % (iid, d['from_lv'], price(it, d['from_lv'] - 1), ons[0], d.get('min_lv', 1), price(tgt, d.get('min_lv', 1) - 1)))
        # apps → home: усе, що позиція тягне, або її власне, або має dep
        for lv, mods in apps.items():
            for m in mods:
                owner = home_of.get(m)
                if not owner or owner == iid: continue
                if owner in roots:
                    continue
                if iid in roots:
                    warns.append('база тягне %s — домашній модуль позиції %s: дубль роботи між Базою і %s' % (m, owner, owner))
                    continue
                ok = any(owner in as_list(d.get('on')) and d.get('from_lv', 9) <= int(lv) for d in deps)
                if not ok:
                    errs.append('%s тягне модуль %s (домашній для %s) з рівня %s, а dep на %s немає або починається пізніше' % (iid, m, owner, lv, owner))
    # цикли жорстких залежностей — не помилка, а ознака кривого скоупінгу
    hard = {iid: {o for d in it.get('dep', []) if d.get('type') == 'hard' for o in as_list(d.get('on')) if len(as_list(d.get('on'))) == 1}
            for iid, it in items.items()}
    for a in hard:
        for b in hard[a]:
            if a in hard.get(b, set()):
                warns.append('взаємна жорстка залежність %s ↔ %s — ознака, що пункт треба перенести в одну з позицій' % (a, b))
    return errs, sorted(set(warns))

def resolve(items, sel):
    """sel: {id: lv_idx 0..2}. Повертає (sel_після, автододані, зауваження)."""
    sel = dict(sel)
    for iid, it in items.items():
        if it.get('req') and iid not in sel: sel[iid] = 0
    auto, notes = {}, []
    changed = True
    while changed:
        changed = False
        for iid, lv in list(sel.items()):
            for d in items[iid].get('dep', []):
                if d['from_lv'] - 1 > lv: continue
                ons = as_list(d['on']); need = d.get('min_lv', 1) - 1
                have = [o for o in ons if o in sel]
                if d['type'] == 'hard':
                    if not have:
                        if len(ons) == 1:
                            sel[ons[0]] = need; auto[ons[0]] = '%s: %s' % (items[iid]['n'], d['why']); changed = True
                        else:
                            notes.append('СТОП %s: потрібна одна з %s — %s' % (items[iid]['n'], ons, d['why']))
                    else:
                        for o in have:
                            if sel[o] < need:
                                sel[o] = need; changed = True
                                notes.append('рівень %s піднято до %d через %s' % (items[o]['n'], need + 1, items[iid]['n']))
                elif not have:
                    notes.append('УВАГА %s без %s — %s' % (items[iid]['n'], '/'.join(items[o]['n'] for o in ons) if len(ons) <= 3 else 'позиції з даними', d['why']))
    return sel, auto, sorted(set(notes))

def total(items, sel):
    return sum(price(items[i], lv) for i, lv in sel.items())

def main():
    price_path = sys.argv[1] if len(sys.argv) > 1 else 'data/price.json'
    frag = sys.argv[2] if len(sys.argv) > 2 else None
    items = load(price_path, frag)
    errs, warns = check_deps(items)
    print('ПОМИЛКИ: %d' % len(errs))
    for e in errs: print('  •', e)
    print('ПОПЕРЕДЖЕННЯ: %d' % len(warns))
    for w in warns: print('  •', w)
    demos = {
        'Каса, рівень Стандарт': {'pos': 1},
        'Оренда, рівень Стандарт': {'rnt': 1},
        'Підписки, рівень Базовий': {'sub': 0},
        'Виробництво, рівень Базовий': {'mrp': 0},
        'Інтернет-магазин, рівень Базовий': {'shop': 0},
        'Виїзні роботи, рівень Розширений': {'fsm': 2},
        'Проєкти, рівень Стандарт': {'prj': 1},
        'Сайт, рівень Базовий': {'web': 0},
        'Склад, рівень Стандарт': {'stk': 1},
        'Мультикомпанійність, рівень 3 + Управлінський облік рівень 1': {'mco': 2, 'acc': 0},
        'Планування, рівень Стандарт': {'pln': 1},
        'Торгівля: База+CRM+Продажі+Закупівлі+Склад(2)+Облік(2)+Бланки': {'crm': 1, 'sal': 1, 'pur': 1, 'stk': 1, 'acc': 1, 'prt': 1},
    }
    print('\nКОНТРОЛЬНІ НАБОРИ (ціна до → після закриття залежностей)')
    for name, sel in demos.items():
        base_sel = dict(sel); 
        for iid, it in items.items():
            if it.get('req'): base_sel.setdefault(iid, 0)
        after, auto, notes = resolve(items, sel)
        print('\n%s: €%d → €%d' % (name, total(items, base_sel), total(items, after)))
        for k, v in auto.items(): print('   + додано %s (рівень %d) ← %s' % (items[k]['n'], after[k] + 1, v))
        for n in notes: print('   ', n)
    return 1 if errs else 0

if __name__ == '__main__':
    sys.exit(main())
```
