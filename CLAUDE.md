# Департамент odoo.com — контекст проєкту

Концепція окремого контуру доставки в компанії Todo: команда працює **тільки** з базами на
Odoo Online (SaaS), без кастомних модулів. Стадія — проєктування, пілоту ще не було.

Мова всіх документів і артефактів — **українська**, навіть якщо обговорення російською.

## Що вже вирішено — не перепитувати

| Питання | Рішення |
|---|---|
| Мотив | новий сегмент SMB + розвантаження основної команди. **Тільки новий вхідний потік**, наявних клієнтів не переводимо |
| Сегмент | UA, малий бізнес. Odoo = операційна система (продажі, закупівлі, склад, проєкти, сервіс, аналітика). Де клієнт веде облік — нас не стосується |
| Модель | прайс-лист модулів із фіксом. Обов'язкова База + вибрані позиції |
| Валюта і ставки | євро. Ставка клієнту **€50/год**, собівартість **€15/год**, резерв на scope **20%** — зафіксовані |
| Роль | **аналітик**, не конфігуратор. Він не клікає в Studio, не пише код, не чистить дані, не пише документацію |
| Хто виконує | **Claude через зовнішній API**: поля, подання, права, довідники, автоматизації |
| API | інструмент впровадження — у скоупі. Послуга клієнту (вебхуки, конектори) — поза скоупом |
| Облік і звітність | **поза контуром повністю** (рішення 05.09.2026): у базі не налаштовуємо бухгалтерський, податковий і кадровий облік, не обіцяємо його й не обговорюємо. Того самого ряду — **фіскалізація каси й способи підписання документів**: у прайсі, чек-листі й КП цих тем немає. Обмін даними з іншими системами клієнта — теж не наша робота ні в якому вигляді |
| Ліцензії | **розгортаємо базу й оформлюємо підписку ми**, клієнт оплачує її **напряму в Odoo за посиланням** (рішення 10.09.2026); ми на ній не заробляємо і в розрахунках не беремо участі. На час робіт адміністративний доступ і ключ — у нас; передача бази = передача прав власнику й анулювання нашого ключа. Нічого не підписуємо — тільки **погодження** (пропозиції, протоколу запуску). Клієнт створює базу сам — ця умова знята. План **Custom** обов'язковий, але **не через Studio** (перевірено 09.09.2026): зовнішнє API — наш спосіб впровадження — за документацією Odoo доступне **тільки на Custom**, а мультикомпанійність теж лишень у Custom. Тобто план не обговорюється навіть тепер, коли Studio ми не відкриваємо |
| Абонемент | у поточному скоупі **немає**. Уся виручка разова, повторний дохід — тільки новий модуль |
| Еталонні бази | немає. Кожен клієнт налаштовується з нуля за процедурою; демо — на стандартному Odoo |
| Старт | пілот на виділених людях, без штату. Штат — за гейтом |
| Ціни в КП | **без ПДВ**. Формулювання «ПДВ додається за законодавством України» прибране (рішення 10.09.2026) — у КП сказано лише «ціни в євро, без ПДВ» |
| Рахунки й оплати | окрема позиція `inv` — власник `account`: журнали, нумерація, умови оплати, банк, каса, реєстрація оплат, **довідник номенклатури** (перевірено 09.09.2026: `account` приносить `product` і `uom`, а застосунки Бази — ні, тому в Базі цього пункту бути не може); жорстка залежність для всіх позицій із рахунками. Плану рахунків, ставок і податкових правил не налаштовуємо. «Управлінський облік» — надбудова про кешфлоу й P&L на документах самої Odoo |
| Навчання | пункти «Навчання команди» не перевіряються в базі, але робота робиться — блок закритий як виконаний (рішення 09.09.2026). Матеріал сесій та письмових інструкцій — `docs/база-знань-блоки.md`: база знань у розрізі блоків прайсу, під кожним пунктом що зроблено і де це в базі. Інструкція ролі складається тільки з **куплених** блоків; загального курсу по Odoo немає |
| Діагностика | «Експрес-діагностика» закрита як виконана і **стоїть першою** в прайсі — група «Вхід у роботу» переставлена наверх (рішення 09.09.2026). Кожен пункт закритий місцем у калькуляторі: скринінг із наслідками, питання по напрямах, банк питань на глибину, анкета клієнта, «не входить» як «сказати відразу», кнопки КП і нотаток. У підсумок КП діагностика не додається — оплачується окремо до старту, і у вартість проєкту зараховується **половина** суми (рішення 10.09.2026): повний залік давав набір, у якому клієнт не доплачував нічого. Частка живе одним числом (`DIAG_CREDIT` у сторінці, звірене з перевіркою), а **девʼята перевірка цілісності** стежить за інваріантом — максимальний залік мусить бути меншим за найдешевший можливий проєкт |
| Мультикомпанійність р.3 | Балансу й P&L у позиції немає (рішення 09.09.2026): замість них **готові зведення по групі на документах** — продажі, закупівлі й рахунки колонками за компаніями, збережені спільними звітами. Зведення в Odoo 19 робить **перемикач компаній**, окремої функції Multi-Ledger немає. Дзеркальні документи між юрособами знято з прайсу: модулі Inter-Company ставимо й налаштовуємо (р.2), автостворення дзеркального документа не обіцяємо |
| Що в Базі р.1 | український фундамент (мова, часовий пояс, валюта, нумерація, 2FA) і оглядова сесія 1 год. Навчання за ролями — окрема позиція |
| Набори (kit) | у позиції «Виробництво» р.1. Тип Combo набори не замінює — складові не списуються (перевірено на стенді 03.09.2026) |
| Партії й серійники | Склад р.2 (не р.3): потрібні харчовим, аптечним і сервісним SMB без кількох складів |

## Межі, які не можна порушувати в обіцянках

Перевірено на живому стенді Odoo 19 — деталі в `docs/аудит-стенд-odoo19.md`.

- У базі клієнта — **тільки штатна конфігурація**. Байдуже, натиснула її людина чи записав інструмент
- **Обчислювані поля на моделі = Python** (Studio не має «Compute») → поза периметром
- **Умови всередині друкованого бланка** правляться лише в XML → замінюємо окремими бланками
- **Прав доступу «на склад» у Odoo немає** → тільки через окремі юрособи
- **Набори (kits) потребують застосунку «Виробництво»** — схована залежність між позиціями прайсу
- **Обліку в базі не робимо взагалі** — план рахунків, ставки, звітність, розрахунок зарплати й кадрові форми поза периметром. Платформні факти про `l10n_ua` лишилися в `docs/аудит-стенд-odoo19.md` як історія перевірки, у прайс і в розмову вони не входять
- **ЄДРПОУ/РНОКПП не перевіряються** (`base_vat` не встановлено) — реквізити контрагентів вносяться без валідації
- **Combo не замінює набори** — складові не списуються зі складу (перевірено продажем на стенді)
- **Українського контуру оплати й доставки немає**: серед 25 платіжних провайдерів і 12 типів доставки — жодного UA. Точка продажу продається як операційний облік продажів і залишків
- **Сума прописом для UAH змішує мови** («Гривня and … Kopiyka») — власний шаблон
- **Переклад інтерфейсу частковий**: меню 95–100 %, підписи полів 60–90 % (project.task — 60 %)
- Кастомні та сторонні модулі, OCA, SQL, cron у базі, успадкування моделей — ніколи

## Як працювати з прайсом

Правити **тільки** `data/price.json` (прайс), `data/qualification.json` (чек-лист) або
`data/client-form.json` (анкета клієнта), далі:

```bash
python3 tools/build_calculator.py
```

**Перед роботою і перед комітом — одна перевірка на весь репозиторій:**

```bash
python3 tools/check_all.py
```

Вона проганяє всі генератори й валідатори і розрізняє два тихі способи все зламати:
**«у коміті стара версія»** (джерело правили, перезбір забули) і **«файл правили
руками, і перезбір цю правку затер»** (похідні файли не правлять — правлять джерело).
Обидва випадки перевірені негативними тестами. Разом із генераторами вона проганяє
**перевірку калькулятора в браузері** — 38 перевірок на сторінках 1–3: ціна рівнів,
автододавання жорстких залежностей, попередження про м'які, збіг суми в КП із панеллю,
поріг обмежень і вердикт «стоп» у чек-листі, розкриття блоків анкети. Якщо в системі
немає `playwright-core` або Chromium, крок позначається **«НЕ ПЕРЕВІРЕНО»** і збірку не
валить: «зламано» і «не перевірено» — різні відповіді. Запустити окремо:
`node tools/test_calculator_ui.js` (код 2 = нема чим перевіряти). Очікувані ціни тест
рахує **з `data/price.json`**, а не тримає числами, тож правка прайсу його не ламає —
але розбіжність прайсу з опублікованим HTML ламає (перевірено навмисним псуванням).
Окремо варто знати, чому взагалі працює порівняння з git: `git diff` екранує кириличні
імена файлів, тому всередині стоїть
`core.quotepath=false` — без нього перевірка молчала б майже для всіх документів
цього репозиторію.

Крім структури окремих файлів збірка перевіряє **цілісність між ними** — девʼять поломок,
кожна з яких тиха (дані валідні, збірка проходить, а прайс починає показувати неправду):
пункт прайсу без запису в журналі перевірки (**попередження**: чернетку писати можна, але
`build_kb` таку позицію пропускає, і обіцянка зникає з усіх звітів); дубль тексту пункту в
позиції (журнал адресує пункт текстом — дубль робить запис неоднозначним); однакова ціна
двох рівнів після округлення до 50 (години зростають, а гроші ні); однакові ознаки рівнів
(за ознакою рівень і вибирають); застосунок у `home` поза власними `apps` (робить фіктивним
попередження «тягнеш чужий модуль без dep»); цикл у жорстких залежностях; **хибне
підтвердження у звірці** — `є: true` разом із `знайшли`, яке лише посилається на іншу
перевірку («перевірено раніше», «те саме, що вище») і не називає жодного доказу: id запису,
назви в лапках чи моделі з полем. Останню додано 10.09.2026, коли з 11 таких записів
**чотири виявились неправдою** — переліки властивостей у базі були порожні. Правило
навмисно не забороняє слово «раніше»: посилання поряд із власним доказом законне, бо сім
із тих 11 записів саме такі. **Восьма** (10.09.2026) — число в прозі проти прайсу:
пояснення чек-листа називає «обовʼязковий мінімум» сумою, а це похідна від прайсу
(«База» р.1 + «Рахунки та оплати» р.1), і поправка годин Бази робить пояснення
неправдою мовчки; отрути дві, бо розійтися можна з обох боків.

**Девʼята** (10.09.2026) — залік діагностики проти найдешевшого можливого проєкту.
Діагностика оплачується окремо, і половина суми зараховується у вартість проєкту; поки
залік був повним, існував набір, у якому він зʼїдав проєкт цілком — діагностика рівня 3
(€1 000) при «тільки Базі» рівня 1 (€800). Половина знімає це арифметично, але не
назавжди: досить підняти години діагностики або опустити години Бази, і випадок
повернеться мовчки, бо числа лежать у різних позиціях прайсу. Тому перевіряється
**інваріант**, а не число, і отрути в неї три — з обох боків і на розсинхрон двох копій
частки (Python перевіряє, JS показує).

Усі девʼять відтворені навмисним псуванням — `python3 tools/test_integrity.py`, він же в
`check_all.py`; у кожної, де правило могло б кричати на правильні дані, є ще й
протиотрута.

**Окремо стережеться клієнтський текст калькулятора** — блок «що не входить», умови,
приймання, опис рівнів: прайс від стоп-слів захищений давно, а статична проза не
перевірялася ніяк, хоча йде клієнтові. Правило дивиться **тільки на код, не на дані**:
у нотатках журналу Studio згадується законно (16 разів — це історія перевірки для
аналітика), і протиотрута перевіряє, що правило туди не лізе.

**Фіксований текст КП** (`NOT_INCLUDED` і `payment()` у `artifacts/calculator.html`) —
єдина частина інструмента **без джерела правди в `data/`**: він живе в коді сторінки,
правиться руками й іде клієнтові. Склад: «що не входить» (7 тем), «два документи
проєкту», «приймання» (6 пунктів), «обовʼязки клієнта» — і **«оплата»**, яка збирається
кодом, бо пункт про діагностику умовний (номери проставляються на місці, інакше або
порожня обіцянка, або дірка в нумерації). Умови оплати: **50 % після підписання і до
початку робіт, 50 % після закриття проєкту**; діагностика окремим рахунком до старту,
залік зменшує перший платіж, а якщо перевищує його — залишок переходить у другий (потрібно
арифметично: залік €500 більший за половину найдешевшого проєкту). Гарантійне вікно —
**15 робочих днів від демонстрації позиції** (5 на зауваження + 10 на дефекти), і той
самий строк — це «супровід запуску», на який посилається «не входить». Загальні умови
проєкту в `bounds` окремої позиції — помилка збірки: 10.09.2026 така копія гарантії лежала
в «Базі». Чотири сторожі: посилання «пункт N розділу «Приймання»» (номер і зміст пункту),
сума 5 + 10 = 15, слово «половина» проти `DIAG_CREDIT`, гарантія в `bounds` — усі з
отрутами, три з протиотрутами.

**Числа в цьому файлі звіряються з даними.** CLAUDE.md — не документація «на потім», а
інструкція, яку читає кожна наступна сесія перед першою дією: застаріле число тут означає,
що робота починається з хибного факту. 10.09.2026 таких чисел було **девʼять**, і частину
зістарив той самий день (додав поле в анкету — «115 полів» стало неправдою; додав тести —
«21 натискання» стало неправдою). `tools/check_claude_md.py` перевіряє **19 тверджень** із
однозначним джерелом у даних і окремо кричить, якщо текст навколо числа переписали й
перевірка перестала на нього дивитися. Гіпотези (години, економія, ставки) і числа з живої
бази тут не перевіряються — їх не можна порахувати з репозиторію.

**Про отруту як обовʼязкову частину правила.** За ніч 10.09.2026 тричі сталося те саме:
перевірка **проходила, дивлячись не туди** — імена подань збиралися лише з аргументів
шаблону; правило про перевірки запускало емітер підпроцесом і читало файл із диска
замість переданого; сторож клієнтського тексту брав «усе до першого блоку даних» як код,
хоча проза КП лежить ПІСЛЯ блоків. Жодну з трьох дірок не показала логіка — усі три
показала отрута, яка не спрацювала. Тому отрута тут не формальність: правило без неї
може бути порожнім і про це не сказати.

Скрипт перевіряє структуру (3 рівні, зростання годин, непорожні ознаки, поля `q`/`bounds`/`dep`,
стоп-слова периметра — «доопрацювання», «доробка», «лише в XML» без застереження) і падає, якщо
зламано. У чек-листі перевіряє вид блоку, наслідок кожної відповіді (`ok|warn|stop`), пояснення
при `warn`/`stop` і посилання `need` на відомі позиції прайсу; у питаннях на глибину — що ключ
збігається з назвою групи прайсу, що питань 8–14, що в кожного є «що слухати» і що кожне
посилання «Назва» рівня N у «що слухати» веде на живу позицію прайсу (скорочена назва —
попередження, перейменована або неоднозначна — помилка); в анкеті клієнта — типи полів,
посилання блоків і розділів на позиції прайсу, 4–8 питань у блоці і **відсутність внутрішньої лексики** (рівні, ціни, «стоп»,
«наш контур», «прайс», «маржа» в питанні до клієнта — помилка збірки). Потім
`artifacts/calculator.html` публікується через Artifact.

**Текст пункту — ключ у ТРЬОХ файлах:** `price.json` (обіцянка), `verify.json` (журнал)
і `recipes.json` (рецепт). Перейменовувати треба скрізь одночасно, інакше збірка падає —
і це добре, бо інакше журнал тихо відстав би від прайсу. Робити це руками не треба:
`python3 tools/rename_item.py "старий" "новий" "причина"` міняє в усіх трьох, дописує
причину в ноту журналу й відмовляється працювати, якщо старий текст трапляється в прайсі
не рівно один раз.

Поля позиції: `inc`, `lv` — склад робіт і рівні; `q` — одне питання сейла, ознаки рівнів — відповіді
на нього; `bounds` — «не входить» (друкується в КП окремим переліком, тому кожен рядок — речення з великої літери); `dep` — залежності `{on, type hard|soft,
from_lv, min_lv, why}`: hard калькулятор додає сам, soft — попереджає; `apps`/`home` — застосунки.
Години й економія — гіпотези до замірів фази 0, їх не міняти без замірів.

Ціна рахується як `години_вручну × 50`, округлення до 50 €. Рівні **вкладені**:
рівень 2 = базові пункти + додані на 2-му, рівень 3 = плюс додані на 3-му.
Назви рівнів однакові по всіх позиціях: **Базовий / Стандарт / Розширений**.

## Інструментарій контуру

Дві генерації поверх джерел правди, обидві перезбираються з нуля:

```bash
python3 tools/build_config_map.py && python3 tools/build_runbook.py
```

- **`data/config-map.json`** — карта налаштування: для кожного з 360 пунктів складу робіт
  моделі Odoo, **модулі**, поля й шлях у меню, витягнуті з поля «де» журналу перевірки.
  Модулі окремо від моделей навмисно: у 24 пунктах адреса — це саме модуль
  («застосунок data_cleaning», «worksheet + industry_fsm_report»), і такий пункт не
  «без адреси» — щоб він працював, модуль має бути в базі. Перелік звірений із
  `ir.module.module`, бо відрізнити модуль від назви поля за виглядом неможливо
  (`partner_id`, `allocated_hours` — теж snake_case). Окремо позначені модулі з
  `auto_install` — вони приходять самі, і в `apps` позиції їх бути не має; без цього
  поділу перевірка «модуль згаданий, а в apps його немає» дала б шість хибних тривог
  із шести. Сама перевірка тепер у збірці карти й закрита негативним тестом. Адресу мають
  **324 пункти**, решта 36 — послуги й дії інтерфейсу. Перелік із 156 моделей **звірений
  із `ir.model` живої бази**, а не вгаданий: хибні кандидати (поля, змінні шаблонів, id
  звітів) лежать окремим переліком `NOT_MODELS`, щоб не знаходилися знову. Якщо після
  правки нот зʼявиться невідомий токен — скрипт скаже про це в консоль.
- **`docs/setup-runbook.md`** — процедура збірки: порядок позицій **топологічним
  сортуванням за жорсткими залежностями** прайсу, застосунки по рівнях, таблиця
  «пункт → модель → шлях у меню».

**Рецепти й план викликів** (з 09.09.2026 працюють, «База» р.1 прогнана цілком):

```bash
python3 tools/check_recipes.py                          # рецепти цілі
python3 tools/emit_config_calls.py профіль.json          # план викликів
python3 tools/emit_config_calls.py профіль.json --всі    # план на ВСІ позиції: покриття
```

**Емітер перечитує готовий план перед друком** і відмовляється його видавати, якщо
там лишилася хоч одна незамінена підставка (`$клієнт`, `$елемент`, `$арг`, `$індекс`,
`$скільки`). Легальним лишається тільки `$імʼя` — посилання на створений запис, яке
розвʼязує виконавець. Сторож зʼявився після двох дірок за один день: обидві давали
**валідний** план із буквальним текстом підстановки всередині значення — емітер не
падав, конектор не сварився, а в базу пішов би запис із `$елемент.назва` в заголовку
подання. Видно таке тільки очима на екрані.

**`--всі` — не документ, а перевірка**, і вона закриває дірку, яка була тихою й великою:
профіль-приклад описує реальний набір клієнта, тому рецепти позицій **поза** цим набором
емітер не бачив ніколи. А саме емітер ловить помилки підстановки — валідатор їх не бачить,
бо поле профілю формально існує. Тобто ціла позиція могла лежати з неробочими рецептами
при зелених перевірках. Тепер `check_all.py` окремим кроком просить план на всі 27 позицій
рівня 3; негативний тест підтверджує, що звичайний план отруту в позиції поза набором
**не бачить**, а `--всі` бачить.

**Дві перевірки, які ловлять те, чого не ловить прогін** (обидві в `check_recipes.py`,
обидві з негативними тестами й протиотрутою):

- **пошук «рівно один» за назвою, якої жоден рецепт не створює.** Рецепти пишуться
  за журналом перевірки, а журнал описує **демо-базу** — де запис уже є, бо його
  заводили руками. «Перейменовано першу чергу» перетворюється на
  `знайти helpdesk.team name = «Підтримка — обладнання»`, і на базі клієнта це
  зупинка на першому кроці. 10.09.2026 таких дірок знайшлося **сім за один прохід**,
  усі в щойно написаних рецептах, і ще дві — щойно правило запрацювало (сім рецептів
  «Сайту» шукали запис `website` за назвою з профілю; правило CRM спрацьовувало на
  стадії, якої не було в переліку стадій). Правило працює на **значеннях** — профіль
  відомий, отже і назви, які план створить, і назва, яку він шукає, конкретні; звужене
  до назв із кирилицею й не чіпає моделей людей, інакше кричало б на штатних записах Odoo.
- **двойники: латиниця серед кирилиці.** «Квалiфiкований» з латинською `i` (U+0069
  замість U+0456) ніколи не збігався з базою — і мовчки. Правило дивиться лише на
  слова з самих літер і лише на латинські літери-двойники (`i`, `o`, `a`, `c`, `e`…),
  бо перша версія кричала на розмітці (`class="container"><h1>Про`) і шляхах
  (`WH/Запаси`), де змішані алфавіти законні. Той самий клас, що апостроф U+2019
  проти U+02BC, який коштував часу **чотири рази**.

`data/recipes.json` — мова з восьми дій: `знайти`, `знайти_xmlid`, `створити` (з
`якщо_немає`), `записати`, `параметр`, `перевірити`, `послуга`, `властивість`.
Остання — про «Властивості», найсильнішу обіцянку прайсу: технічно це не поле, а рядок
у переліку-визначенні на **батьківському** записі (контрагент → спільний запис
`properties.base.definition`, задача → проєкт, товар → категорія, обладнання → категорія
обладнання, співробітник → компанія). Пара «де властивості» → «де визначення» знята
з живої бази й **перевіряється валідатором**: помилка тут тиха — властивість ляже не
туди, де її шукає Odoo, і в картці не зʼявиться. Контракт дії — читання-зміна-**читання
назад**, тому окремого `перевірити` після неї не потрібно (запис визначення замінює весь
перелік, а не додає рядок). Прогнано кінець-у-кінець: категорія «Кавомашини» →
властивість `potuzhnist_kvt` → значення 2,3 на кавомашині. Підстановки: `$клієнт.поле`
з профілю (підставляє емітер) і `$імʼя` — посилання на запис, що зʼявиться при виконанні.
Валідатор ловить посилання на невизначений запис, невідоме поле профілю, перейменований
пункт і невідому дію.

**Периметр перевіряється й у плані, не тільки в прайсі.** Стоп-слова стережуть
обіцянку клієнту, але план, який цю обіцянку виконує, до 10.09.2026 не перевірявся
ніяк. Тепер валідатор забороняє **писати** в `ir.cron`, `ir.model`, `ir.module.module`,
`account.account`, `account.tax`, `account.tax.group`, `account.fiscal.position`,
`hr.contract`, `hr.payslip`, `hr.salary.rule`, а також сервер-дію зі `state` «code»
(Python у базі) чи «webhook» (вебхуки — послуга поза скоупом; значення взяте зі списку
вибору живої бази, а не з голови) і власне поле з `compute`/`depends`. **Читання цих
моделей дозволене навмисно:** три рецепти «Підписок» саме читають `ir.cron`, щоб
переконатися, що штатне розписання Odoo живе. Пʼять отрут і протиотрута — у
`test_integrity.py`.

**Імена полів, які пише план, звірені з базою:** 290 пар «модель + поле» у 79 моделях
проти `ir.model.fields` — одна помилка (`maintenance.equipment.location`, насправді
`location_id` на `stock.location`, тобто прихована залежність від «Складу»). Перелік
пар готує `tools/probe_fields.py` → `docs/поля-плану-для-звірки.md`; сам він у базу не
ходить (ключа API в репозиторії немає) і стоїть у збірці, щоб перелік не застарів.

**Проба доменів** (`python3 tools/probe_recipes.py профіль.json --всі`) — про найчастішу
поломку рецепта, яку валідатор не бачить: **домен, що знаходить не те**. Крок із
`один: true` обіцяє «рівно один запис», і перевіряється ця обіцянка лише читанням бази.
Проба збирає такі домени з **розгорнутого плану** й відділяє ризик від шуму: пара
«створити → знайти» всередині плану самодостатня (на свіжій базі запис зʼявиться), тому
кричати треба лише про записи, які мусять існувати **до** плану. Знає й про неявні
створення (`product.template` тягне за собою `product.product`), інакше кричала б і на них.
**`--всі` обовʼязковий**, і це не зручність: без нього проба бачить лише позиції з
набору профілю — тобто ті рецепти, які й так найбільше прогнані. На повному плані
130 пошуків «рівно один», 57 унікальних доменів. Прохід 10.09.2026 дав три поломки:
проєкт, який план створює сам, шукався за жорстким `id`; виїзний проєкт теж за `id`
(ні id, ні назва не годяться — назву перекладають, тому домен за ознакою `is_fsm`);
перевірка властивості казала «перечитуємо значення», а перевіряла лише існування
контрагента. **Проба не замінює валідатор:** ще два жорсткі id стояли в
`батько_домен` кроків `властивість`, а проба збирає тільки `знайти`. Друга поломка того ж
проходу: шаблон листа шукався за назвою «Order Confirmation», а він зветься «Sales:
Order Confirmation». Звідси правило: **штатний запис Odoo адресуємо зовнішнім id, а
не назвою** — назву перекладають разом з інтерфейсом, а «Базу» р.1 ми починаємо саме
з української мови. Записи, які клієнт перейменовує під себе (стадії заявок, базова
одиниця), лишаються назвами з профілю.

**Два переліки «звірити з базою» стали сторожами.** Валідатор друкував імена
батьківських подань і зовнішні id із підписом «цього я не бачу» — підпис правдивий і
тому марний. Тепер обидва звірені з базою (**9 імен подань**, кожне дає рівно один
запис; **40 зовнішніх id**, усі знайдено) і заморожені в `check_recipes.py`. Незнайоме
значення валить збірку: це єдина перевірка, яка ловить не помилку, а **незнання** —
ім'я може бути правильним, але поки його не прочитали з бази, воно не їде до клієнта.
Привід був конкретний: `maintenance.equipment.form` не існує (коренева форма зветься
`equipment.form`), причому журнал це вже раз записував, а потім стара назва повернулася
в шаблон.

**Поломка, яку знайшла саме проба, а не прогін:** рецепт «умови оплати й банківські
реквізити» шукав `res.partner` за назвою клієнта з профілю, щоб покласти на нього
банківський рахунок. Але банківський рахунок належить партнерові **власної компанії**, а
назва компанії в базі й назва клієнта в профілі — різні рядки: на демо-базі компанія
зветься «Тодо — демо-стенд Odoo Online». Крок «рівно один» не знайшов би нічого. Тепер
партнер береться з `res.company.partner_id` — для цього в мові зʼявилася підстановка
**`$імʼя.поле`** (поле знайденого запису, розвʼязує виконавець), і валідатор ловить у ній
описку в базовому імені (перевірено негативним тестом).

**Три речі, які прогін довів дорогою ціною:** `знайти_xmlid` обовʼязковий (id груп на
кожній базі свої); `якщо_немає` робить рецепт повторюваним; **пошук головної компанії
доменом «без батька» небезпечний** — на базі з кількома юрособами перейменує не ту, тому
цільова компанія називається в профілі полем `компанія_id`, а перед записом стоїть
підрахунок юросіб.

**Тринадцять шаблонів** покривають найповторюваніші артефакти прайсу: `робоче_місце`
(15 разів у прайсі), `власне_поле` (14), три види кнопок (13) — `кнопка_ознака`,
`кнопка_стадія`, `кнопка_завдання` — і `узгодження_за_сумою` (контур «поріг суми → віза →
узгоджено» продано в чотирьох позиціях); далі `правило_записів`, `штатна_поведінка`,
`послуга_передачі` і три шаблони друкованих бланків.

**Три шаблони бланків — це три різні механізми, а не варіанти одного** (усі перевірені на
живій базі): `бланк_копія` — подання `primary` з `inherit_id` на штатне подання документа
плюс власна дія звіту, копія зʼявляється в меню «Друк» поруч зі штатним і нічого нікому не
ламає; `бланк_власний` — подання `primary` **без** `inherit_id`, верстка з нуля, для
документів, яких у Odoo немає взагалі (акт передачі, специфікація); `правка_бланка` —
подання `extension` з `xpath` у штатний бланк, діє на **всі** документи цього виду.
Пастка, записана в шаблон: `report_name` дії мусить дорівнювати **ключу подання** слово
в слово — інакше звіт існує, у меню видно, а друк падає, бо шукає неіснуючий шаблон. Дві пастки платформи, зняті з бази й записані в
самих шаблонах: **поле-перелік без варіантів створюється порожнім** (варіанти — окремі
записи `ir.model.fields.selection`, і валідатор вимагає `опції` саме для типу
`selection`); **дія сервера, що пише значення переліку, тримає його у двох місцях** —
`value` (код) і `selection_value` (посилання на варіант), тому варіанти мусять існувати
до правил. Шаблон описаний один раз і викликається з аргументами;
розгортає його емітер. Кроки шаблонів валідатор перевіряє так само, як кроки рецептів —
інакше зламаний шаблон проїжджає (спіймано на цьому).

**Рецепти виду «штатна поведінка» дописує генератор** — `tools/gen_standard_recipes.py`.
Це не суперечить правилу «не генерувати рецепти»: те правило про **конфігурацію**, де
склад полів і домени залежать від клієнта й вигадати їх не можна. У «штатній поведінці»
вигадувати нічого — записувати в базу не треба, робота складається з двох однакових для
всіх кроків: переконатися, що застосунок став (перевіряємо наявність **моделі**, бо на
свіжій базі документів ще немає), і показати процес на живих документах. Копіювати такий
рецепт пʼятдесят разів означало б розмножити текст, який ніхто не перечитає.

`check_all.py` генератор **не запускає**, а лише питає його «--dry»: він пише в
`data/recipes.json` — джерело правди, а не похідний файл, і мутувати джерело автоматично
означало б, що склад рецептів змінюється без рішення людини. Тому перевірка каже
«зʼявилося N пунктів виду «штатна поведінка» без рецепта» і залишає запуск людині
(перевірено негативним тестом — прибрав один рецепт, збірка це назвала).

Кожен згенерований рецепт має поле `джерело`, і звіт рахує їх **окремо** від рукописних —
інакше готовність виглядала б завищеною. Генератор ідемпотентний: наявних рецептів не
чіпає, тож будь-який згенерований можна замінити рукописним. Валідатор щоразу перечитує
вид пункту: якщо в журнал дописали адресу й пункт став конфігураційним, згенерований
рецепт **занижує роботу** — план виглядає повним, а налаштування ніхто не зробить, — і
про це сказано вголос (перевірено негативним тестом).

`tools/report_recipe_gaps.py` → `docs/рецепти-що-лишилось.md` каже, **де рецептів немає і
який шаблон підходить**: **360 із 360 описано** (296 рукописних, 64 згенерованих),
не лишилося жодного.

**«ОПИСАНО» — ЦЕ НЕ «ПЕРЕВІРЕНО», і звіт тепер каже це вголос саме тоді, коли в ньому
нуль.** Рецепт на кожен пункт означає рівно одне: **план збірки більше не має дірок**,
жоден пункт не зникне з нього мовчки. Прогнано на живій базі близько сотні кроків
(«База» р.1, «Проєкти й таймшити» р.1 і шаблони кінець-у-кінець); решта написана
за журналом перевірки — за тим, що на базі вже робили руками, — і звірена з
`ir.model.fields`, але через конектор не проганялась. Практичний висновок: перший
клієнтський прогін кожної позиції — це перевірка рецепта, а не тільки збірка бази. Звіт навмисно **не генерує рецепти сам**: склад полів у поданні й домени
залежать від клієнта, а правдоподібний і неправильний рецепт — найгірший результат, бо його
ніхто не перевірить.

Повністю закриті рівні 1 у «Базі», «Рахунках та оплатах», CRM, «Продажах», «Складі» й
«Проєктах й таймшитах». **Усі 27 позицій закриті рецептами повністю — 360 пунктів із 360, 870 кроків.**
План на весь прайс рівня 3 — 1 114 кроків і 1 507 викликів конектора. Прогнано на живій базі понад 100 кроків; профілі складалися з поточних
значень бази, тому всі створення пропускалися як наявні — це й була перевірка
повторюваності.

Дія **`для_кожного`** розгортається **емітером**, а не виконавцем: профіль уже відомий,
тому замість циклу виконавець отримує конкретні кроки. Поруч `$скільки($клієнт.поле)` —
щоб перевірка кількості була точним числом. **У вкладеному кроці `назвати` не має сенсу** —
записів буде кілька, і посилання вказувало б на останній; валідатор це ловить. Часто цикл
узагалі зайвий: `знайти` без `один` повертає кілька записів, і `записати` пише в усі
разом — один виклик замість N.

**Власне поле «(штатно)» можливе не скрізь.** Моделей із полем «Властивості» рівно 20 —
перелік знято з `ir.model.fields` живої бази 10.09.2026 і лежить у `_схема` файлу
`data/recipes.json` разом із таблицею «де властивості → де їх опис» (15 власників опису).
Серед 20 **немає** `project.project`, `hr.expense`, `res.company`, `sale.order`,
`purchase.order`: на них власне поле робиться тільки механізмом «власне поле +
успадковане подання», і обіцянка «(штатно)» для них неправдива.

Ознака рівня пишеться **мовою ситуації клієнта, а не мовою функцій**: не «до 20
користувачів, права роздільні за ролями», а «до 5 ролей з різним доступом до застосунків»;
не «P&L за напрямами», а «прибуток по напрямах бізнесу». Сейл має пізнати ситуацію з
розповіді клієнта, а не звіряти числа.

## Чек-лист кваліфікації — друга сторінка калькулятора

Той самий файл `artifacts/calculator.html`, перемикач сторінок у верхній стрічці. Розділи
вмикаються **галочками** у стрічці розділів і відкриваються **по одному**: вибір нового розділу
закриває попередній, тому на екрані тільки те, про що говорять зараз.

- **Клієнт і набори** у стрічці: сейл вписує назву клієнта й тисне «Зберегти» — набір
  (позиції, рівні, відповіді скринінгу, глибина, розкриті розділи) лягає в окремий ключ
  `odoo-com-calc-cases-v1` під цією назвою. Селект перемикає клієнтів, «Видалити» прибирає набір,
  «Почати заново» чистить поточний стан, але **збережені набори не чіпає**.
- **Скринінг** — 14 питань-гейтів із `data/qualification.json`: розмір, облік, готовність працювати в стандарті, людина з правом рішення, роздріб, зарплата, номенклатура, оплата й доставка, канал спілкування, обсяг міграції, обов'язкові інтеграції, юрособи, валюта. Серед них гейт про облік: «чи очікує клієнт, що система вестиме облік, податки або зарплату» — відповідь «так» це `stop`. І гейт про **бюджет** (рішення 10.09.2026): єдина названа сума — €1 100, і це не оцінка ринку, а арифметика прайсу («База» р.1 + «Рахунки та оплати» р.1, нижче прибирати нічого). Відповідь «нижче мінімуму» — `warn`, а не `stop`: у схемі `stop` означає «лід іде в основну команду», а такий клієнт туди не піде — там дорожче. Число стереже **восьма перевірка цілісності**: сума в поясненні порівнюється з порахованою по прайсу, отрути з обох боків — правка тексту й правка прайсу. Кожна відповідь має наслідок:
  `ok` — працюємо як звичайно, `warn` — обмеження, яке сейл каже вголос **до КП**, `stop` —
  дискваліфікація, лід іде в основну команду. Відповідь може нести `need` — позиції прайсу,
  які вона робить обов'язковими: `"mig"` або `{"on":"mig","lv":3}` — тоді кнопка не просто додає
  позицію, а ставить її не нижче названого рівня («підняти «Базу» до рівня 2»).
- **Напрями** — сім груп прайсу. Питання позиції (`q`) з ознаками рівнів як варіантами
  відповіді: вибір одразу проставляє позицію й рівень у калькуляторі, «не потрібно» знімає її.
  Під обраною позицією друкується її `bounds` як «сказати відразу».
- **«Розкрити глибину»** у кожному напрямі — 10–14 питань із ключа `глибина` у
  `data/qualification.json`, по одному ключу на назву групи прайсу. У питання немає готових
  відповідей: клієнт розповідає сам, а поле `hear` («що слухати») підказує сейлу, який рівень
  або яку межу означає почуте. Галочка = «спитали»; лічильник стоїть у заголовку розділу
  («відповіли 3 / 5 · глибина 4 / 14») і потрапляє в нотатки зустрічі. Ставити всі не обов'язково —
  це банк питань на 84 позиції, з якого сейл бере те, що потрібне цьому клієнту. **До рівня кожної
  позиції прайсу веде хоча б одне питання** — перевіряється зіставленням назв позицій із текстами
  «що слухати».
- **Поріг обмежень:** чотири відповіді «з обмеженням» і більше піднімають прапорець «звірити
  з керівником», шість і більше — «інший профіль клієнта, рішення керівника». Поріг потрапляє
  і в нотатки зустрічі рядком «УВАГА: N обмежень».
- Кнопка «Зібрати нотатки» дає внутрішній текст зустрічі: відповіді, обмеження, склад із
  ознаками, що не потрібно, що ще не питали. Це **не** КП — КП збирається на першій сторінці.

Стан обох сторінок спільний і лежить в одному ключі localStorage; «Почати заново» чистить усе.

Блок виду `чеклист` (умови старту галочками) збірка ще розуміє, але таких блоків у даних немає —
рядок «Готовність» у панелі з'являється сам, якщо додати блок цього виду в JSON.

## Повний перелік — четверта сторінка (СХОВАНА)

**Сторінка схована від користувача, але не видалена** (рішення 10.09.2026): у публікації
для сейла входу до неї немає — це внутрішній довідник аналітика. Керує одним рядком у
коді сторінки: `var СХОВАНІ = ['spec']`. Вхід закритий з трьох боків — кнопка вкладки,
вміст і підзаголовок ховаються на старті, `ПОРЯДОК` стрілок фільтрується, а прямий
`showPage('spec')` перекидає на першу сторінку. Читалка теж не побачить: `hidden` прибирає
з дерева доступності, тому «вкладка 2 з 3». Повернути = прибрати id зі списку.
`check_hidden_pages` стежить за **обома** твердженнями — що вона схована і що розмітка
на місці; три отрути (повернули у вкладки, видалили розмітку, зник перелік).

Далі — опис самої сторінки, він чинний: її вмикають і вона працює.

Довідник по всьому прайсу: **позиція → рівень → пункти складу робіт**, згенерований із
`GROUPS`, тобто з `data/price.json`. Своїх даних не має — це проєкція, і після правки прайсу
оновлюється сама.

- Під кожним рівнем першим рядком стоїть **ознака** (за нею рівень і вибирають), далі пункти.
- Рівні вкладені, тому за замовчуванням під рівнем 2 і 3 стоїть **тільке додане на ньому**
  (позначка «додається до попереднього»). Перемикач **«накопичено»** показує повний склад рівня.
- Перемикач **«не входить»** показує `bounds` кожної позиції.
- **Типовий вигляд сторінки** (рішення 09.09.2026): «сховати позначені» і «галочки» увімкнені,
  «накопичено» і «не входить» — вимкнені. Тобто відкривши сторінку, бачиш **тільки те, що
  лишилося зробити**. «Очистити пошук» повертає рівно цей набір. Лічильник у стрічці рахує
  **видимі** позиції і пункти («18 позицій · 106 пунктів · сховано 254»), а заголовок групи,
  у якій усе закрито, ховається разом із позиціями. Коли відкритих пунктів не лишилося зовсім,
  «сховати позначені» на старті **не вмикається** — інакше довідник відкривався б порожнім.
- **Пошук** фільтрує по всіх 548 рядках (360 пунктів складу + 81 ознака + 107 рядків «не входить») —
  найшвидший спосіб перевірити, чи обіцяли ми колись конкретну річ і в якій позиції.
- Перемикач **«сховати позначені»** прибирає з екрана пункти, які вже позначені: рівень,
  де позначено все, зникає цілком, позиція без живих пунктів — теж. Ознака рівня лишається
  (за нею рівень і вибирають), лічильники далі показують повні числа, а в стрічці зʼявляється
  «сховано N». Разом із фільтром «показати позначені» перемикач не працює — вони взаємно
  виключні. «Очистити пошук» повертає сторінку до типового вигляду.
- Сторінка зроблена **під друк**: `@media print` прибирає стрічку, вкладки, панель і футер,
  лишаючи тільки позиції, і не розриває позицію між сторінками.

## Анкета для клієнта — третя сторінка (прототип)

Те саме вікно, вкладка «Анкета для клієнта». Заповнює **клієнт** перед зустріччю, тому мова
інша: жодних рівнів, цін, «стопів» і слова «контур» — збірка падає, якщо внутрішня лексика
потрапила в питання. Джерело правди — `data/client-form.json`.

- **Постійні розділи**: про компанію, що болить, дані, люди й строки, що ще — 35 полів.
  У розділів теж може бути `позиції` (about → `base`, data → `mig`) — для майбутнього зіставлення.
- **Блоки процесів** (15) з'являються тільки після того, як клієнт позначив галочкою, що йому
  потрібно: 81 питання його мовою, 4–8 на блок (більше клієнт покине — збірка попереджає).
  Кожен блок має `позиції` — id позицій прайсу, щоб відповіді потім можна було зіставити з
  набором; клієнт цього не бачить. Серед блоків є «Навчання команди» і «Кілька юросіб або ФОП»
  — позиції `trn` і `mco`, яких в анкеті бракувало.
- Типи полів: `текст`, `абзац`, `вибір` (радіо-кнопки з `опції`).
- Кнопка «Скопіювати відповіді» дає текст із заповненими питаннями (порожні не друкуються) —
  клієнт надсилає його листом чи в мессенджер. Автоматичного надсилання немає й не буде без
  окремого рішення.
- Вступ називає межу клієнту вголос: «Odoo налаштовуємо як операційну систему… облік у ній
  не ведемо».

**Сторінка самодостатня — так задумано, щоб винести її в окремий файл:** свій ключ localStorage
(`odoo-com-client-form-v1`), свої стилі `.f*`, свій блок JS між коментарями
«АНКЕТА КЛІЄНТА (сторінка 3)» і «кінець блоку анкети клієнта». Вона нічого не читає й не пише
у стан сторінок сейла. Щоб винести: узяти `data/client-form.json`, розмітку `#page-form`, блок
стилів `.f*` і блок JS — решта калькулятора правок не потребує. Поки не винесено, **клієнту
посилання давати не можна**: у тому ж вікні видно вкладки з цінами.

## Перевірка прайсу на живій базі — галочки на четвертій сторінці

Прохід виконано 09.09.2026 на `edu-online-todo.odoo.com`: **усі 81 рівень і всі пункти**
складу робіт, потім другий прохід по всьому, що не вийшло, потім закриття блоків
«Навчання команди» й «Експрес-діагностика» і прогін міграції відкритих документів.
Результат — **360 із 360 налаштовано й перевірено, відкритих пунктів немає**. У кожного
пункту в журналі записано, що саме зроблено і де це в базі; там само сказано, чого
перевірка не покриває — вигляд екранів записами не перевіряється, картинку дивиться людина.

Джерело правди — `data/verify.json`: `id позиції → рівень «1|2|3» → пункт → {с, нота, де, звірка}`.
**Два шари, які не треба змішувати:** `с`/`нота`/`де` — що ми **робили** (історія проходів);
`звірка` (дата, дивились, знайшли, є) — що **справді є в базі** на день звірки. Звірка 09.09.2026
дала 276 із 360, після проходу «завести те, що заводиться» — 343 із 360; після
переперевірки 10.09.2026 — **342 із 360 знайдено в базі, 18 немає**. Число впало на одиницю
не тому, що щось зламалось, а тому, що `prj` р.2 «власні поля в проєкті й задачі» виявився
закритим лише наполовину: задача має властивості, а **`project.project` немає серед 20
моделей із полем `ttype = properties` взагалі**, тому власне поле на самому проєкті
«Властивостями» зробити не можна. Решта 17 — те, чого в базі й не буває: навчання й виїзд
як послуги, звіт майстра імпорту, вивантаження в Excel, мобільний вигляд.
**Меж конектора серед них немає.**
Повний журнал — `docs/звірка-бази-2026-09-09.md`, що саме заведено — у журналі налаштування,
поведінка інструмента — у `docs/база-знань-налаштувань.md`.

**Головна пастка інструмента, перевірена дорого:** конектор часто повідомляє помилку там,
де дія відбулася — він не серіалізує відповідь методу, а не провалює виклик. Чотири пункти
я через це записав як «межа конектора» (рядки складського переміщення, Auto Plan,
зіставлення виписки, проведення списання) — усі чотири насправді працюють. **Правило:
після кожної відмови перечитувати запис; помилка конектора не є доказом межі.** Друге
правило звідти ж: якщо читання моделі падає, ламає його **конкретне поле** — бити навпіл
(на `stock.move` це `name`), а не вважати модель закритою.
Статуси: `ok` (налаштовано й перевірено), `fail` (не вийшло або припущення хибне),
`move` (належить іншій позиції), `skip` (у базі перевіряти нічого). Збірка перевіряє,
що текст пункту слово в слово збігається з прайсом (перейменування ламає збірку) і що
`fail`/`move`/`skip` мають пояснення. На сторінці в кожного пункту дві різні речі:
**відмітка журналу** з нотою та шляхом у Odoo (це запис про демо-базу, він у git) і
**особиста галочка** (localStorage, ключ `odoo-com-calc-verify-v2`) — це відмітка про
**базу конкретного клієнта**, тому галочки **типово зняті** (рішення 09.09.2026): відкривши
сторінку, аналітик бачить порожній чек-лист на 360 пунктів, а не «усе вже зроблено».
Кнопка в стрічці працює в обидва боки — «Позначити все», якщо база вже налаштована за
прайсом, і «Зняти всі», щоб почати з чистого на новому клієнті. Є лічильники по рівнях і
позиціях і фільтр «не позначені / позначені / проблемні» (останній читає журнал, а не галочки).

**Другий прохід показав: більшість відмов інструмента були одноразовими** — те, що не
проходило з першого разу, пройшло з другого. Через конектор працюють: рахунки (майстер
із замовлення + проведення), оплати (майстер реєстрації), журнали й умови оплати,
рядки виписки, **успадковані подання з xpath** (власні поля в документах — перевірено
на замовленні продажу й специфікації), дії сервера з привʼязкою до моделі й роллю
(кнопки в меню «Дії»), копії звітів з обмеженням роллю, сторінки сайту (копія подання
+ запис сторінки), шаблони підпису Sign із полем на координатах.

**Третій прохід (09.09.2026, ніч) закрив 23 із 25 відкритих** — і двічі виправив мій власний
хибний діагноз: виробниче замовлення не закривалося через **невказану партію** матеріалу, а не
через майстра; вміст сторінок сайту й форми, що створюють лід, **пишуться через конектор** у
`arch` подання, а не тільки в конструкторі. Шаблон узгодження за рівнями (поле-перелік +
поле-віза з групою ролі + правило на порозі суми) перевірений на продажах, закупівлях,
витратах і погодженнях. Друкований бланк перевірений відрендереним документом.

**Що лишилося закритим:** `ir.ui.view.group_ids` не пишеться ні при створенні, ні при правці,
ні через `write` як метод (перевірено тричі). Але **результат досягається інакше й це те, що
ми продаємо**: роль обмежується на **пункті меню** — подання з режимом `primary` (власний
макет) + дія з `view_id` і фільтром + `ir.ui.menu.group_ids` (пишеться). Перевірено на CRM
і Складі; так само обмежені штатні меню Odoo. Поле й дію теж можна обмежити роллю
(`ir.model.fields.groups`, `ir.actions.server.group_ids`). Лишаються закритими: закриття
виробничого замовлення; дзеркальні документи Inter-Company; видалення й архівування записів.

**Пастка, на якій я сам зламав базу:** `res.company.external_report_layout_id` посилається
на **`ir.ui.view`**, а не на запис `report.layout` — підставлений id зі списку layout-ів
поклав рендер усіх звітів (500 на кожному). Правильні id — подання
`external_layout_boxed`, `_striped`, `_bold` тощо.

**Головна змістова знахідка:** у Odoo 19 частина моделей має «Властивості» — власні
поля описуються з інтерфейсу без Studio й без правки подань (контрагент, угода,
задача, товар, партія, складська операція, зміна планування, заявка, картка
співробітника, запит погодження). Перелік залежить від набору встановлених
застосунків, тому на кожній базі його перечитують заново.

**Слова «Studio» у прайсі більше немає** (рішення 09.09.2026): усі 45 пунктів, де воно стояло,
мають статус «налаштовано й перевірено», і в кожного в журналі записаний штатний шлях —
«Властивості», власне поле плюс успадковане подання, дія сервера з привʼязкою й роллю,
правило записів або штатний модуль. Сім пунктів, де перевірка показала саме «Властивості»,
позначені «(штатно)» — це сильніша обіцянка: без правки подань і без ризику на оновленні.
Наслідок, який лишався відкритим, **закритий 09.09.2026**: план Custom клієнтові потрібен
однаково, і причина сильніша за Studio — зовнішнє API за документацією Odoo доступне тільки
на Custom, а це і є наш спосіб впровадження. Деталі й цитата — `docs/база-знань-налаштувань.md`.

**Опублікована версія калькулятора може бути новішою за репозиторій** — його правлять і з
самої сторінки артефакту. Перед роботою з прайсом звірити — це одна команда:

```bash
# спершу прочитати артефакт інструментом Artifact (action: "read") — він зберігає
# повний HTML на диск і друкує шлях; далі:
python3 tools/check_artifact.py <шлях-до-збереженого.html>
```

Скрипт звіряє **дані й код окремо**, бо це різні поломки. Дані — п'ять вшитих блоків
(`GROUPS`, `QUAL`, `PROBES`, `FORM`, `VERIFY`) — порівнюються **з джерелами правди**
`data/*.json`, а не з HTML у репозиторії: одна перевірка ловить і «правили на сторінці,
у репозиторій не перенесли», і «правили тут, сторінку не перепублікували». Порівняння
за розібраним JSON, тому відступи й порядок ключів не значать нічого. Розбіжність
друкується адресою з людською підказкою — `GROUPS[1].items[0].lv[0][1] (Основа · «База» ·
рівень 1)`, а не дифом на 690 КБ. Код сторінки (розмітка, стилі, JS) порівнюється окремо:
будь-яка різниця означає, що правку робили в артефакті і **вона зникне при наступній
публікації з репозиторію**. Обгортку публікації скрипт відрізає сам. Перевірено чотирма
негативними тестами: зміна годин у рівні, зміна тексту пункту, правка `var RATE` у коді,
зникнення блоку.

## Артефакти

вони додаються при публікації. Щоб подивитися локально, треба обгорнути:

```bash
python3 - <<'PY'
import io
s = io.open('artifacts/calculator.html', encoding='utf-8').read()
io.open('/tmp/preview.html','w',encoding='utf-8').write(
  '<!doctype html><meta charset="utf-8"><meta name="viewport" content="width=device-width,initial-scale=1">' + s)
PY
```
